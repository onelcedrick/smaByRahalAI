RAPPORT DE PROJET
Système Multi-Agents et Théorie des Catégories pour le Traitement de Commandes

1. Introduction
Le présent projet a pour objectif de démontrer l’unification de trois paradigmes fondamentaux de l’informatique et des mathématiques : la Modélisation (représentation structurée des processus), les Systèmes Multi-Agents (SMA) (informatique distribuée et autonomie), et la Théorie des Catégories (abstraction des relations et des compositions).
Pour ce faire, nous avons conçu et développé une application web de bout en bout simulant une chaîne de traitement de commandes logistiques. Un client soumet un produit via une interface ergonomique ; le système orchestre quatre agents autonomes pour valider, payer et expédier la commande, tandis qu’un superviseur vérifie en temps réel que le chemin emprunté respecte rigoureusement les lois de la composition catégorique. Ce rapport détaille l’architecture, les choix techniques, l’implémentation et le fonctionnement du système.

2. Architecture Globale
Le système suit une architecture client-serveur robuste et modulaire, découpée en quatre couches distinctes :
    1. Couche Présentation (Frontend) : Interface utilisateur réactive en HTML5/CSS3/JavaScript natif. Elle permet la saisie des commandes, l’affichage des logs temps réel et la consultation de l’historique.
    2. Couche API (Backend) : Serveur REST développé avec FastAPI (Python). Il expose des endpoints pour soumettre une commande (/run) et consulter l’historique (/history).
    3. Couche Métier (Noyau SMA) : Ensemble de modules Python implémentant les agents, le bus de messages, le superviseur et le foncteur. Cette couche est indépendante du web et peut être exécutée en mode terminal.
    4. Couche Persistance : Base de données SQLite locale (fichier sma.db) stockant l’intégralité des commandes traitées, leur chemin et leur statut final.
Schéma fonctionnel :
[Client Web] --(HTTP)--> [API FastAPI] --(Appel)--> [Noyau SMA]
                                                         |
                                                         v
                                                 [Agents Parallèles]
                                                         |
                                                         v
                                              [Superviseur / Foncteur]
                                                         |
                                                         v
[Affichage Logs] <--(Résultat)-------- [Base de données SQLite]

3. Le Pilier 1 : Modélisation
La modélisation constitue la source de vérité du système. Elle définit les états possibles d’une commande ainsi que les transitions autorisées.
3.1. La Catégorie
Nous avons défini une catégorie mathématique représentant le cycle de vie d’une commande.
    • Objets (États) : Created, Verified, Paid, Shipped, Delivered.
    • Flèches (Transitions) : Verify, Pay, Ship, Deliver.
Structure du graphe :
Created --(Verify)--> Verified --(Pay)--> Paid --(Ship)--> Shipped --(Deliver)--> Delivered
3.2. Implémentation
Dans le module src/modelisation.py, le dictionnaire CATEGORY matérialise ce graphe :
CATEGORY = {
    "Created": {"Verify": "Verified"},
    "Verified": {"Pay": "Paid"},
    "Paid": {"Ship": "Shipped"},
    "Shipped": {"Deliver": "Delivered"},
    "Delivered": {}
}
La fonction get_next_state(current_state, arrow) retourne l’état suivant si la flèche est applicable, sinon None.
La fonction compose(start_state, arrows) vérifie la composition d’une séquence de flèches, appliquant ainsi la loi d’associativité fondamentale de la théorie des catégories.

4. Le Pilier 2 : Système Multi-Agents (SMA)
Le SMA est le moteur exécutif du système. Il est composé d’agents autonomes qui communiquent de manière asynchrone via un bus de messages.
4.1. Le Bus de Messages (MessageBus)
Le bus centralise les échanges. Chaque agent possède sa propre boîte aux lettres (queue.Queue). L’envoi de messages est non-bloquant et thread-safe.
4.2. Les Agents
Chaque agent hérite de la classe Agent (sous-classe de threading.Thread) et surcharge la méthode process(message).
Agent	Rôle	Traitement Métier
Réceptionniste	Interface initiale	Valide le format du formulaire. Crée l’état Created.
Vérificateur	Gestion des stocks	Simule une vérification de disponibilité (80% de succès). Applique la flèche Verify vers l’état Verified.
Banquier	Traitement financier	Simule une autorisation de paiement (70% de succès). Applique la flèche Pay vers l’état Paid.
Logisticien	Expédition	Génère un numéro de suivi. Applique les flèches Ship et Deliver pour atteindre l’état Delivered.

4.3. Parallélisme
Les agents s’exécutent en parallèle (multithreading). Ils réagissent aux messages déposés dans leur file d’attente, ce qui rend le système décentralisé et réactif.

5. Le Pilier 3 : Théorie des Catégories
Cette couche mathématique valide et transforme le comportement du système, apportant une rigueur formelle au processus métier.
5.1. Le Superviseur (Superviseur)
Le Superviseur est un agent spécial (thread) qui agit en tant qu’observateur.
    • Interception : Le MessageBus lui envoie une copie de tous les messages échangés.
    • Validation : Le Superviseur reconstruit l’historique de la commande. À la fin du traitement (statut TERMINATED ou FAILED), il vérifie que chaque transition entre états successifs existe bien dans le graphe CATEGORY.
    • Rapport : Il génère un rapport final avec le statut VALID (si la composition est respectée) ou INVALID (violation). Ce rapport est stocké en base de données.
5.2. Le Foncteur (Foncteur)
Le Foncteur est une abstraction de haut niveau qui transforme globalement le comportement du SMA sans modifier le code des agents.
    • Principe : Il agit comme une "lentille" de traduction entre les flèches théoriques du modèle et les actions réelles des agents.
    • Modes implémentés :
        ◦ Mode normal : Exécution standard des transitions.
        ◦ Mode debug : Application de délais artificiels et ajout d’informations de logging supplémentaires.
    • Impact : Le changement de mode s’effectue via l’interface utilisateur. Les agents restent identiques ; seul le Foncteur modifie le routage et les paramètres d’exécution.

6. Persistance des Données (Base de Données)
La persistance est assurée par SQLite.
Schéma de la table orders :
CREATE TABLE orders (
    id INTEGER PRIMARY KEY,
    product TEXT,
    price REAL,
    quantity INTEGER,
    status TEXT,
    path TEXT,
    tracking_number TEXT,
    error TEXT,
    mode TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
Les données sauvegardées incluent le chemin catégorique validé (path), le statut final (VALID, FAILED, INVALID), et les éventuelles erreurs métier. Cette traçabilité permet une analyse a posteriori du comportement du SMA.

7. Interface Utilisateur (Frontend)
L’interface est conçue pour être à la fois fonctionnelle et pédagogique.
7.1. Disposition (Grille 2 colonnes)
    • Colonne Gauche :
        ◦ Formulaire "New Order" : Saisie du nom du produit, du prix, de la quantité, et sélection du mode (normal ou debug).
        ◦ Tableau "History" : Liste des commandes déjà traitées, extraites de la base SQLite. Affichage du statut, du chemin et du numéro de suivi.
    • Colonne Droite :
        ◦ Panneau "Processing Logs" : Affiche en temps réel les étapes du SMA.
7.2. Indicateur Dynamique d’Agent
Une fonctionnalité innovante a été intégrée : un indicateur visuel change en fonction de l’agent actif.
    • Icônes textuelles :
        ◦ [R] pour le Réceptionniste (Couleur bleue).
        ◦ [V] pour le Vérificateur (Couleur jaune).
        ◦ [B] pour le Banquier (Couleur verte).
        ◦ [L] pour le Logisticien (Couleur violette).
        ◦ [S] pour le Superviseur (Couleur cyan).
    • Comportement : Lors de la simulation, l’icône et le label se mettent à jour à chaque étape, suivant le flux de la commande (Réceptionniste → Vérificateur → Banquier → Logisticien → Superviseur). Cette animation rend le fonctionnement distribué du SMA tangible pour l’utilisateur final.
7.3. Mode "Réel" vs "Simulation"
Le frontend simule visuellement les étapes (pour une expérience utilisateur fluide) tout en appelant l’API réelle en arrière-plan. Le résultat de l’API (provenant du noyau SMA et du Superviseur) vient confirmer ou infirmer la simulation, assurant l’intégrité du processus.

9. Démonstration et Résultats
Le système a été testé sur plusieurs cas de figure :
    • Parcours nominal : La commande traverse tous les états. Le Superviseur valide le chemin Created -> Verified -> Paid -> Shipped -> Delivered avec un statut VALID. L’interface affiche le succès et le numéro de suivi.
    • Échec métier (Stock/Rupture) : L’agent Vérificateur échoue. Le chemin reste partiel (Created -> Verified). Le Superviseur enregistre un statut FAILED avec le message d’erreur.
    • Transformation par Foncteur : En mode debug, des latences sont observables dans le panneau de logs, prouvant l’intervention du Foncteur sans modification du code métier.

10. Conclusion
Ce projet remplit avec succès son objectif principal : illustrer l’interaction puissante entre la Modélisation, les Systèmes Multi-Agents et la Théorie des Catégories.
    • Point fort : L’architecture modulaire permet d’isoler parfaitement les couches (métier, mathématique, web). La preuve de la composition catégorique est automatisée et vérifiée à l’exécution.
    • Innovation : L’interface utilisateur ne se contente pas de soumettre des données ; elle visualise le flux distribué des agents via un indicateur dynamique, rendant l’abstraction mathématique concrète.
    • Perspectives : Le système peut être étendu à des cas d’usage plus complexes (réseaux de neurones pour les décisions des agents, déploiement en conteneurs Docker, ou intégration de nouvelles flèches et objets dans la catégorie).
L’application est stable, portable (grâce à SQLite) et prête à être démontrée en contexte académique ou professionnel.
